## 2. 脚本能力

### `scripts/backup.sh`

- 在 MySQL 健康后执行一致性逻辑备份，任一等待、导出、压缩、附件归档或校验失败非零退出。
- 生成数据库备份、附件归档、SHA-256、manifest、Flyway 版本和行数/对象计数快照。
- 不记录或打印数据库密码。

### `scripts/restore.sh`

- 恢复前必须同时校验 manifest 和备份 SHA-256，不信任单独文件名。
- 默认拒绝非空目标；仅显式授权才能进入覆盖路径。
- 目标项目必须使用恢复专用前缀，环境文件内项目名必须完全匹配，MySQL/附件卷必须以该目标项目精确命名；生产项目名和卷无法通过预检。
- MySQL 未健康、等待超时、导入失败、校验失败或表/角色/用户/Flyway 数量不一致时立即非零退出，不输出“恢复完成”。
- 恢复运行在独立 Compose 项目和独立数据卷，不复用源库数据卷。

## 4. 隔离环境必须演练的验收步骤

1. 使用 GitHub Actions 只构建并推送三个 `linux/amd64` SRM业务镜像到 TCR，记录短SHA标签和三个不可变 digest；MySQL/Nginx 使用Compose固定的官方版本，不属于自研镜像。
2. 在独立项目`srm-stage1-acceptance`以 MySQL 8.4 创建空库，执行 V1–V12；另建隔离V3基线执行 V4–V12，验证原数据保留和重启无待执行迁移。
3. 执行 `scripts/backup.sh`，保留数据库备份、附件归档、manifest、SHA-256 和日志。
4. 用一个非空目标验证默认拒绝；再在全新隔离卷执行 `scripts/restore.sh`。
5. 比对表数（应用表 48，含 Flyway 历史表共 49）、角色、用户、V12 迁移版本、关键行计数和附件 SHA-256。
6. 按 `deploy/STAGE1_ACCEPTANCE.md` 执行严格目标校验；仅全部校验通过后将本报告状态更新为“演练通过”，并附实际时间、镜像 digest、命令、退出码和校验值。
