# 阶段0：SRM 系统工程架构与功能骨架开发及整改报告

记录日期：2026-07-24  
依据：`SRM_V1.0_阶段0_系统工程架构与功能骨架搭建任务书.docx`

## 1. 结论与范围

阶段0 S0-01～S0-08 的代码、配置、脚本、文档及全部非 Docker 验收项已完成。当前基线能够以本地非容器方式实际启动、登录、刷新令牌、退出、鉴权、加载动态菜单、访问页面，并由内部管理端调用后端标准分层接口。

本轮整改补齐了正式生产部署模板、Springdoc/OpenAPI 开关、工作台标准分层链路、启动期敏感配置拒绝策略及 H2/Flyway 兼容版本。未增加真实业务 CRUD、业务表、模拟交易、伪 KPI、流程引擎或供应商真实身份与数据隔离。

2026-07-23～24 已完成 Docker 专项补验：五服务、真实 MySQL 8.4、Nginx 代理和数据卷
持久化均已实际运行。2026-07-24 又将 `flyway-core` 与 `flyway-mysql` 从 10.20.1 对齐至
首个满足 MySQL 8.4 范围的稳定版本 11.15.0，并完成隔离空库专项复验。当前 P0、P1 均为
0，详细证据见《阶段0Docker专项验收报告》和《阶段0 Flyway P1 整改复验报告》。

2026-07-24 又完成独立真实性复核及三项架构优化：全部运行时 Spring JDBC 数据访问迁移
至 MyBatis-Plus 3.5.17；动态菜单通过 Spring Cache/Caffeine 受控缓存；内部/供应商双
OpenAPI 规范、lint、破坏性变更检查、TypeScript 类型和 API 客户端生成接入全量门禁。
隔离开发与生产 Compose 五服务均已重新实测，详见《阶段0架构优化与独立复验报告》。

## 2. 本轮整改结果

### 2.1 生产部署模板

- 新增 `deploy/docker-compose.prod.yml`，包含 mysql、backend、internal-web、supplier-web、nginx 五个服务。
- 五个服务均配置健康检查，依赖链使用健康状态，MySQL 使用可配置的持久化命名卷。
- 后端固定使用 `prod` profile、安全 Cookie，生产 OpenAPI 固定关闭；应用镜像、数据库参数、CORS、JWT 和启动账号密码均使用必填环境变量。
- 新增 `deploy/prod.env.example` 和 `deploy/README.md`；示例秘密保持为空，模板不能被当作可直接部署的密码文件。
- 新增 MySQL 安全入口校验，拒绝缺失、过短、`CHANGE_ME`、示例或占位密码。

### 2.2 OpenAPI

- 引入 Springdoc 2.7.0，与 Spring Boot 3.4.x 兼容。
- development 默认开启且可由 `SRM_OPENAPI_ENABLED` 关闭；test 默认关闭但测试可按需显式开启；production 固定关闭。
- 自动化测试验证：开启时 `/v3/api-docs/internal`、`/v3/api-docs/supplier` 与 Swagger UI
  可用；关闭时全局及两组规范和 UI 均返回 404，同时正常业务接口仍可访问。

### 2.3 标准分层链路

- 在 workbench 域建立 Controller、Application Service、QueryService、Domain Model、Repository 契约、MyBatis-Plus Mapper/适配器和 Response DTO 的完整链路。
- `GET /api/v1/workbench/baseline` 通过 `workbench:home:view` 鉴权，执行参数化 `SELECT 1` 仅验证基础设施连接，不查询或保存业务数据。
- 内部端工作台通过类型化 API 客户端调用该接口并展示 `READY`，建立后续模块可复制的真实模板。
- 单元、集成、前端静态契约和 ArchUnit 边界测试覆盖该链路。

### 2.4 配置安全

- Spring Boot `ApplicationContextInitializer` 在 Bean 创建和数据库连接前校验 JWT、启动账号及数据库秘密。
- 缺失、长度不足、空白、占位符、示例值、弱口令和管理员/查看者相同密码均会使启动失败。
- production 还强制刷新 Cookie 为 Secure；直接绕过 `start-local.sh` 启动也无法使用占位秘密。
- 生产缺失 JWT 和使用 `CHANGE_ME` 的可执行 JAR 启动均实测退出码 1。

### 2.5 H2 与迁移

- H2 从 2.3.232 调整为 Flyway 当前明确支持的 2.2.224。
- V1、V2、V3 三个迁移从空 H2 MySQL 兼容库执行成功，迁移文件数量与开发报告、验收记录及文件清单一致。
- 重新运行测试后不再出现 H2 超出 Flyway 支持范围的提示。
- Flyway 由 Spring Boot BOM 默认的 10.20.1 显式对齐为 core/mysql 11.15.0；无需升级
  Java 17 或 Spring Boot 3.4.1。
- 真实 MySQL 8.4.10 隔离空库成功执行 V1～V3，重启 backend 不重复迁移，重建 MySQL
  容器并保留数据卷后历史和数据仍存在；原兼容性警告扫描为 0。

### 2.6 架构优化

- 用户/角色、刷新会话、审计、动态菜单和 workbench 数据访问全部迁移到 MyBatis-Plus；
  代码扫描为零直接 JdbcTemplate，4 个复杂 Mapper XML 均关闭二级缓存并使用参数绑定。
- Spring Cache 当前使用 Caffeine，只缓存用户动态菜单元数据；容量 256、TTL 5 分钟，
  角色分配按 userId 精确失效，不缓存实时交易状态且未部署 Redis。
- internal/supplier 双 OpenAPI 从实际 Controller 导出，Redocly 规范校验、相对 baseline
  的 breaking change、静态文档、共享 TS 类型和 openapi-fetch 客户端漂移全部纳入
  `scripts/check.sh`。
- production 实际容器内两组 API docs 和 Swagger UI 均 404；业务冒烟同时通过。
